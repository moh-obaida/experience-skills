# Precedent: Playful Products with Real Mechanics

Use this module when enjoyment, curiosity, characters, or social energy are part of the product's
value. The transfer rule is consistent across the examples: personality belongs in the world,
content, feedback, or social loop; the control still needs to be easy to understand and operate.

## `PLY1`

**Observed:** Scratch makes interactive stories, games, animations, sharing, remixing, and
collaboration the product loop; its editor has stable stage, sprite, block, and script regions.

**Right when:** the product's object is something the user creates and shares.
**Transfer:** let the content and creation loop provide the play, with stable spatial roles for
tools. **Wrong when:** decorative animation competes with the object being made.

## `PLY3`

**Observed:** Finch ties small goals to a pet's energy, adventures, reflections, breathing, focus,
and customization.

**Right when:** a character can make a repeated self-care or habit action feel approachable.
**Transfer:** connect the character to real progress and offer non-competitive paths. **Wrong when:**
the mascot reacts without changing the user's understanding of state.

## `KH1`

**Observed:** Kahoot puts a join code in a saturated environment and leaves the input plain.

**Right when:** the product has one obvious entry value and a shared social setting.
**Transfer:** playful environment, standard input, forgiving paste/focus behavior. **Wrong when:**
custom input animation becomes the task.

## `BK1`

**Observed:** Blooket uses a repeated tilted-square motif and a single Game ID input to make the
join surface recognizable without custom control chrome.

**Right when:** one environmental motif can carry identity across a simple entry state.
**Transfer:** repeat one world-building carrier; keep the submit path obvious. **Wrong when:** every
component becomes a different sticker or shape.

## `DU1`

**Observed:** Duolingo makes the owl character the focal image and offers both a new-user path and a
visible returning-user path.

**Right when:** character continuity helps users understand the product's emotional stance.
**Transfer:** define character poses and recovery states, and preserve return paths. **Wrong when:**
the character replaces a clear task label or account action.

## `BR1`

**Observed:** Brilliant uses an actual puzzle problem as the hero visual rather than a generic
illustration.

**Right when:** the content itself is surprising or rewarding.
**Transfer:** make the thing users will think about or manipulate the visual focus. **Wrong when:**
playful imagery is unrelated to the lesson or tool.

## `KA2`

**Observed:** Khan Academy routes teachers and learners separately from the first surface instead of
forcing one playful onboarding story on both audiences.

**Right when:** different audiences have materially different goals.
**Transfer:** make playful entry audience-aware and preserve the consequential route. **Wrong when:**
one tone or character is used to blur role differences.

## `DI1`

**Observed:** Discord uses a specific illustrated gaming/hangout world, while its download/browser
choice remains an ordinary, OS-aware action.

**Right when:** the product's social world is part of the reason to enter.
**Transfer:** make the environment specific and preserve platform-aware choices. **Wrong when:** the
world obscures the first action or assumes every visitor is a gamer.

## `PLY4`

**Observed:** Finch's self-care tools include breathing, focus, reflections, and small goals; the
playful layer supports several emotional states rather than only celebration.

**Right when:** the product needs gentle entry, persistence, and recovery, not just rewards.
**Transfer:** design quiet, incomplete, missed-day, and restart states before celebration states.
**Wrong when:** the product punishes absence with loud streak loss or forced cheer.

## Transfer checklist

1. Put personality in environment, content, character, sound, or event feedback before styling a
   basic control.
2. Keep labels, focus, paste, keyboard, screen-reader names, and target sizes conventional.
3. Define success, failure, waiting, missed-progress, and return-user states—not only celebration.
4. Test reduced motion, flashing limits, audio alternatives, color-independent feedback, and
   multilingual text expansion.
5. Ask whether the product still works when the character/art layer is removed. If not, the mechanic
   is probably under-specified.
